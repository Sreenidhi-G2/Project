# VeriFace

**A fraud-verification layer for identity submission points — built for Razorpay's Open Track.**

VeriFace looks at a photo or video submitted during KYC (a selfie, a video-KYC liveness check) and tries to answer one question: *is this actually a real, unmanipulated person, or has it been tampered with or generated by AI?*

That question matters more than it used to. Fraud rings can now use face-swapped video to fool liveness checks during merchant onboarding, and — increasingly — someone doesn't even need face-swap tools anymore. They can just type a prompt into Gemini or GPT and generate a convincing fake selfie from scratch. This project builds detection for **both** of those attack paths, not just one, and is honest about where each one still falls short.

---

## The problem, in plain terms

Razorpay's onboarding and payment flows lean on video-KYC, selfie-matching, and liveness checks — all of which assume the face on camera is a real, live person matching the claimed identity. That assumption is breaking in two different ways:

1. **Face-swap / reenactment deepfakes** — someone takes a real video and swaps in a different face, or reenacts someone else's expressions onto it. This is the "classic" deepfake.
2. **Fully AI-generated content** — someone doesn't touch a real video at all. They generate a synthetic face or video from scratch using a diffusion model (Gemini, GPT image/video generation, Midjourney, DALL-E, Stable Diffusion). No face-swap software needed — just a text prompt.

These two attack types look similar to a human eye but are architecturally very different under the hood, which is why VeriFace is really **two specialist detectors working together**, not one model trying to do everything.

---

## What VeriFace actually does today

- Scores both **images** (a KYC selfie/document photo) and **videos** (a liveness-check clip)
- Runs **two specialist models** on every face it sees:
  - a **face-swap/reenactment detector**, trained on FaceForensics++
  - an **AI-generated-content detector**, trained on a mix of Midjourney, DALL-E, and Stable Diffusion output
- For video, aggregates per-frame scores (mean, max, and variance) instead of judging a single frame
- Uses a **three-tier decision system** — auto-approve, auto-flag, or route to manual review — instead of a single brittle threshold, because a single cutoff either lets fraud through or over-flags genuine users
- Explains itself with a **Grad-CAM heatmap** showing which part of the face triggered a flag, plus a one-line plain-English reason
- Exposes everything through a **FastAPI backend** with prediction logging, so results aren't just a notebook output

## The results (the honest version)

I tested this rigorously rather than reporting one flattering accuracy number. Here's what actually happened.

### Face-swap / reenactment detector
Trained on FaceForensics++ (fine-tuned EfficientNet-B4), 300 videos per manipulation category.

| Test | AUROC |
|---|---|
| Held-out test split (same dataset) | 0.79 |
| Cross-dataset generalization (Celeb-DF, official benchmark split, never seen in training) | 0.63 |

Broken down by manipulation method:
Deepfakes **0.92** → FaceSwap **0.84** → Face2Face **0.82** → NeuralTextures **0.70**

That ordering matches published literature almost exactly — NeuralTextures is the hardest because it only manipulates the mouth region, which is a well-known result in this field, not something I'm claiming to have discovered.

### AI-generated-content detector
This one had a real debugging story (see below). Final version, trained on a mixed generator set (Midjourney + DALL-E + Stable Diffusion):

| Test | AUROC |
|---|---|
| Held-out test split (same distribution) | 0.95 |
| Cross-generator check (Stable Diffusion XL, a generator not in this training mix) | 0.56 |

That 0.56 isn't a great number, and I'm not going to pretend it is. Cross-generator generalization for AI-image detection is a genuinely hard, actively-researched open problem — even well-resourced research teams struggle with it. Broadening the training data helped a little (an earlier SDXL-only version scored 0.52 on unseen generators — pure chance), but it didn't solve it. I think that's a more honest and more interesting finding than a clean "it works perfectly" claim would be.

## The debugging story (the part I'm actually proud of)

The first training run of the face-swap detector looked broken: **0.98 AUROC on training data, 0.55 on validation** — essentially random guessing on unseen videos. Rather than just tuning hyperparameters and hoping, I ran a diagnostic that broke validation performance down **by manipulation method** rather than looking at one blended number. That test showed near-chance performance uniformly across every method — including Deepfakes, which is normally the easiest one to detect. That ruled out "some methods are just hard" and pointed at something structural.

The actual cause: I'd only pulled 100 source videos per category, meaning the "real" class was built from roughly 100 distinct people. The model was memorizing *specific faces* from training, not learning what manipulation looks like in general — so none of that shortcut transferred to the different people in the validation set. Scaling to 300 videos per category fixed it: validation AUROC jumped from 0.57 to 0.82, and the per-method breakdown suddenly matched the pattern published research would predict.

The same instinct caught a second problem later: an early AI-generated-photo detector scored a suspicious **0.9999** validation AUROC — too perfect to trust. A cross-generator test (evaluating it against Midjourney/DALL-E instead of the Stable Diffusion it was trained on) confirmed it: performance collapsed to 0.52, basically chance. The model hadn't learned "AI-generated vs. real" — it had learned to tell apart two different data-export pipelines. That's the kind of shortcut that never shows up in a same-dataset test split, only in a genuinely out-of-distribution one.

I also tested the video pipeline against my own webcam footage and a Gemini-generated video, not just benchmark data. Two personal clips showed the face-swap model producing borderline false-positive scores — a real, quantifiable domain gap between studio-lit benchmark footage and consumer camera video. And the Gemini video initially slipped through as "REAL" on average, even though a couple of individual frames scored very high — which is why the decision logic now escalates on a single high-confidence outlier frame, not just the average.

None of these were comfortable findings in the moment, but they're the reason I trust the final numbers more than I would if everything had just worked on the first try.

## Known limitations (said out loud, not buried)

- **Cross-generator AI-content detection is weak** (0.56 AUROC on an unseen generator). This needs either a much broader multi-generator training set or an ensemble of generator-specific specialist models — a real open problem, not a quick fix.
- **The face-swap detector shows a false-positive tendency on personal camera footage** — a domain gap between FaceForensics++'s training footage and real consumer webcam/phone video. Would need broader real-world calibration data before production use.
- **No dedicated AI-generated-video detector** — the AI-content specialist was trained on photos, and is applied per-frame to video as an approximation. It's not trained on video-diffusion-specific artifacts directly.
- **The AI-content detector's decision thresholds are estimated, not rigorously tuned** — unlike the face-swap detector, which had a proper threshold sweep against Celeb-DF.
- **Out of scope for this build**: real-time video-call stream analysis, voice/audio deepfake detection, adversarial robustness hardening.

## How it's built

```
veriface/
  ml/
    preprocessing/     # frame extraction, face crop/align, dataset prep scripts
    training/           # model.py, dataset.py, train.py, evaluate.py,
                        # cross_dataset_eval.py, cross_generator_eval.py,
                        # video_inference.py, video_inference_ensemble.py,
                        # gradcam_explain.py, diagnose_by_category.py
    checkpoints/         # face-swap detector weights
    checkpoints_ai_v2/    # AI-generated-content detector weights (final version)
  backend/
    app/                  # FastAPI: main.py, inference.py, database.py, schemas.py
  frontend/               # (in progress)
```

**Models**: EfficientNet-B4 (via `timm`), fine-tuned for binary classification, both specialists sharing the same architecture.
**Face detection/cropping**: MTCNN (`facenet-pytorch`).
**Explainability**: Grad-CAM (`pytorch-grad-cam`), targeting the backbone's final conv layer.
**Backend**: FastAPI, SQLite for prediction history/audit trail, models loaded once at startup.

## Running it

```bash
# ML environment
pip install torch torchvision opencv-python facenet-pytorch timm albumentations \
            scikit-learn pytorch-grad-cam pandas tqdm

# Backend
pip install fastapi uvicorn python-multipart sqlalchemy pillow

cd backend/app
python -m uvicorn main:app --reload
# then open http://127.0.0.1:8000/docs
```

## A note on data

The raw video datasets (FaceForensics++, Celeb-DF) and extracted face-crop datasets are **not in this repo** — they're large, and FaceForensics++/Celeb-DF both carry usage terms that don't allow public redistribution. They're stored separately in Google Drive: **https://drive.google.com/drive/folders/1OXvFCpYAFtl7zKF8ULPOlZtt9beYiNnp?usp=drive_link**. The trained model checkpoints (`ml/checkpoints/`, `ml/checkpoints_ai_v2/`) are small enough to live in the repo directly, or can go in Drive too if you'd rather keep the repo lean — your call.

If you're picking this project back up, the fastest path is: download the checkpoints, skip straight to the backend, and only re-run the `ml/preprocessing/` scripts if you actually need to retrain from raw video.
